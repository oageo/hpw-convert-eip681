# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`hpw-convert-eip681` is an **unofficial, unaffiliated** bidirectional converter between HashPort Wallet payment links and EIP-681 (ERC-681) payment URIs: HashPort link → EIP-681 URI (or its components: address, amount), and EIP-681 URI → HashPort link. It performs pure client-side string/URL parsing only — it never sends any network request to HashPort's servers (or anywhere else). Currently supports only JPYC, on four chains selected by `master_currency_id`: `487` = Polygon (chain id 137), `489` = Avalanche C-Chain (43114), `490` = Ethereum (1), `712` = Kaia (8217). Other chains/currencies are explicitly rejected, not silently ignored, in both directions.

HashPort link format (parsed by the forward direction, generated by the reverse direction):
```
https://link.expo2025-wallet.com/pay?to=<address>&master_currency_id=<id>&amount=<hex>&to_name=<label>&type=<type>
```
Accepted EIP-681 subset (reverse direction input; forward direction output omits `pay-` and emits only `address`/`uint256`):
```
ethereum:[pay-]<JPYC contract>@<chain id>/transfer?address=<to>[&uint256=<amount>]
```

A generated HashPort link is only meaningful if the recipient address is the one registered in HashPort Wallet; the library can't verify that (no network access). The README documents this caveat — keep it there if touching the reverse-direction docs.

Two-crate Cargo workspace:
- `core/` — pure Rust, published to crates.io as `hpw-convert-eip681`.
- `wasm/` — wasm-bindgen wrapper around `core` (path dependency), built with `wasm-pack` and published to npm as `hpw-convert-eip681` (the crate itself is named `hpw-convert-eip681-wasm` to avoid a name collision with `core` inside the workspace, and is renamed post-build — see below). Not published to crates.io (`publish = false`).

## Commands

All commands run from the repo root unless noted.

**Build / lint / test (core + wasm, native target):**
```
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```
Run a single test: `cargo test -p hpw-convert-eip681 <test_name>`. Most behavior is covered by integration tests (not unit tests in `src/`): `core/tests/parse.rs` (HashPort link → `ParsedLink`), `core/tests/eip681.rs` (EIP-681 → `ParsedLink`, incl. round trips and rejection cases), `core/tests/to_hashport.rs` (`ParsedLink` → HashPort link, incl. byte-identical round trip of real HashPort-generated links).

If `serde` feature-gated code needs checking: `cargo clippy -p hpw-convert-eip681 --all-targets --features serde -- -D warnings` (the `wasm` crate always builds `core` with `features = ["serde"]`, so this is what actually gets compiled for npm).

**wasm build (requires `wasm-pack`; install via `cargo install wasm-pack --locked`, not the `jetli/wasm-pack-action` marketplace action — that action's version resolution has been observed to install a stale `wasm-pack` build that fails to parse Cargo.toml workspace-inheritance syntax like `license.workspace = true`):**
```
wasm-pack build wasm --target nodejs --out-dir pkg-node --out-name hpw_convert_eip681
node wasm/tests/smoke.mjs
```
```
wasm-pack build wasm --target bundler --out-dir pkg --out-name hpw_convert_eip681
node wasm/scripts/finalize-package.mjs
```
**Gotcha:** the first positional argument to `wasm-pack build` (`wasm`) is the crate path, and `--out-dir` is resolved *relative to that crate path*, not the current working directory. Running `wasm-pack build wasm --out-dir wasm/pkg` from the repo root double-nests the output into `wasm/wasm/pkg`. When invoking from the repo root, always use `--out-dir pkg` (not `wasm/pkg`).

`wasm/scripts/finalize-package.mjs` is a required post-build step, not optional polish: `wasm-pack` emits `pkg/package.json` with the Rust crate name (`hpw-convert-eip681-wasm`); the script renames it to `hpw-convert-eip681`, sets description/license/repository, and copies the repo-root `LICENSE` and `README.md` into `pkg/` (neither crates.io-style `license.workspace` nor wasm-pack's own README auto-detection reaches files outside the crate directory, so this has to be done by hand). It also ships `wasm/types/errors.d.ts` as `pkg/errors.d.ts` and appends `export type { HpwParseError } from "./errors.js";` to the generated main `.d.ts` (type-only; the runtime `.js`/`.wasm` files are untouched). The `.js` extension is deliberate: the package is `"type": "module"`, so TypeScript's `nodenext` resolution rejects an extensionless relative import. It's idempotent (dedupes `package.json`'s `files` array via `Set`, and skips the re-export line if already present), so re-running it is safe.

## Architecture

### Conversion pipelines (`core/src/`)

`ParsedLink` is the shared intermediate representation; every conversion is "parse into `ParsedLink`" + "render from `ParsedLink`":

```
HashPort link --parse()--------> ParsedLink --to_eip681()--------> EIP-681 URI
EIP-681 URI  --parse_eip681()--> ParsedLink --to_hashport_link()--> HashPort link
```

`parse_eip681()` always yields `to_name`/`link_type` = `None` (EIP-681 has no equivalent); callers set the `pub` fields before `to_hashport_link()` if they want them. `to_eip681()` is infallible; `to_hashport_link()` returns `Result` (`UnsupportedChain`) because `ParsedLink`'s fields are `pub` and can hold a (currency, chain) pair with no `master_currency_id`.

**Forward (`parse::parse()`)**: `is_supported()` is a thin `.is_ok()` wrapper over it. Pipeline order, each step returning on first error: URL parse → exact host match (`constants::EXPECTED_HOST`, case-insensitive via `url` crate's own normalization, no suffix matching — rejects spoofing like `link.expo2025-wallet.com.evil.example`) → single-pass query extraction → currency + chain resolution (`Currency::from_raw_id`) → address parse (lenient, no checksum enforced) → amount decode (hex, `0x`-prefix optional) → construct `ParsedLink`.

**Reverse (`eip681::parse_eip681()`)**: hand-written (no `url` crate — `ethereum:` URIs aren't hierarchical URLs). Char-level check → scheme (`ethereum:`, case-insensitive, optional `pay-`) → split on first `?`, `/`, `@` → token address → contract lookup (`Currency::from_contract_address`) → chain id → function name → params → recipient → amount. The module doc in `eip681.rs` lists every rule and its rationale — keep it in sync when changing behavior.

Module split mirrors these pipelines and the `ParseError` variant families: `constants.rs` (all magic values — JPYC contract address, chain ids, host, link scheme/path, currency ids — centralized here rather than scattered, mirroring the author's other project `jpyc-payment-qr`'s `constants.ts` convention), `error.rs`, `currency.rs` (the `SUPPORTED` id table), `amount.rs` (hex decode + encode), `address.rs` (lenient / strict / EIP-55-if-mixed parsers), `link.rs` (`ParsedLink`/`AddressAmount`/`ChainId` + both renderers), `parse.rs` (forward pipeline), `eip681.rs` (reverse pipeline + EIP-681 decimal number parser).

Non-obvious invariants worth knowing before touching this code:
- **`amount` is `Option<U256>`, not `U256`.** The source URL sometimes omits the `amount` param entirely; that's `None`, not an error. `to_eip681()` omits `&uint256=` from the output URI when absent (EIP-681 allows amount-unspecified transfer requests). A present-but-empty `amount=` *is* an error (`InvalidAmount`) — don't conflate the two.
- **Hex decoding must go through `strip_prefix("0x"/"0X")` + `U256::from_str_radix(_, 16)`, never bare `U256::from_str`.** The bare `FromStr` (backed by `ruint`) auto-detects radix and defaults to decimal for unprefixed input, so an unprefixed all-digit amount like `"1000"` would silently be misparsed as decimal 1000 instead of hex 0x1000 — a value-corruption bug, not a caught error.
- **The empty-string check in `amount.rs` is load-bearing, not cosmetic.** `ruint`'s `from_str_radix` returns `Ok(0)` for an empty string rather than erroring, so without the explicit check, `amount=` or `amount=0x` would silently parse as amount zero.
- **So is the hex-digits-only check before `from_str_radix`.** `ruint`'s `from_str_radix` silently skips `_` (digit separator), so without it `amount=_` / `amount=0x__` slip past the empty check and parse as zero, and `0x1_000` is accepted. The same trap applies to any new `from_str_radix` call (the reverse direction's decimal parser validates digits itself before calling it).
- **Generated `amount` is always `0x` + 64 lowercase hex digits, zero-padded** (`format!("{amount:#066x}")` — width 66 includes the `0x`). This is byte-identical to real HashPort-generated links (tested by round-tripping real links in `to_hashport.rs`); don't "simplify" to minimal hex.
- **`master_currency_id` identifies a (currency, chain) pair, not a currency.** HashPort assigns a separate id per chain for the same token. The single `SUPPORTED` table in `currency.rs` holds every (id, currency, chain) row and is read by both directions (`Currency::from_raw_id` forward, `Currency::master_currency_id` reverse), so the two directions can't drift apart; adding a chain is one row. Neither `parse()` nor `parse_eip681()` has chain logic of its own. Only ids observed in real HashPort-generated links are accepted; don't add ids by interpolation (e.g. `488` sits between supported ids and is deliberately rejected).
- **Forward parsing is lenient, reverse parsing is strict — deliberately asymmetric.** Forward input comes from HashPort itself, and the output (an EIP-681 URI) is shown to a wallet that has its own confirmation UI. Reverse output is a HashPort link that *decides* recipient/amount/chain, so any input that wallets could interpret differently is an error rather than a best guess. Concretely, in `parse_eip681`: chain id is required (EIP-681's "current network" default can't map to a `master_currency_id`, and defaulting to mainnet could make someone pay on the wrong chain); leading-zero chain ids are rejected; function must be exactly `transfer`; recipient only via `address=`; duplicate params → `DuplicateParam` (forward is last-wins — see below); `value=` and unknown params → `UnsupportedParam` (dropping them would change the payment's meaning); only `gas`/`gasLimit`/`gasPrice` are accepted-and-ignored; ENS names rejected (resolution needs network); `0x` required; whitespace/control/non-ASCII/`#` rejected, no trimming; percent-decoding never maps `+` to space (`+` is a sign in EIP-681's number grammar). Don't relax these to match the forward parser.
- **Mixed-case addresses in EIP-681 input must pass EIP-55** (`address::parse_address_eip55_if_mixed`); all-lower/all-upper are accepted. Neither existing helper works for this: alloy's `Address::from_str` (used by lenient `parse_address`) is a plain hex decode that does **not** verify mixed-case checksums, and `validate_checksum` rejects uniform case.
- **`uint256=` uses EIP-681's decimal number grammar, including scientific notation** (`2.014e18`), with exact-integer and U256-range checks. It must run in time linear in input length even for `1e99999999999999999999`: digit count is bounded *before* computing `10^exp`. Never compute a power from an attacker-controlled exponent. Hex (`0x10`) is rejected, never reinterpreted.
- **Generated `to_name`/`type` percent-encode everything except RFC 3986 unreserved chars, and space is `%20`, never `+`.** HashPort's decoder is unknown: `%20` decodes to space under both form-decoding and `decodeURIComponent`, `+` doesn't under the latter. Encoding `&`/`=`/`#`/`%` is what prevents `to_name` from injecting other params (tested). `None` → param omitted; `Some("")` → `to_name=`; this distinction round-trips through `parse()`.
- **`Currency::contract_address()` takes no chain argument** because JPYC is deployed at the same address on all four supported chains (`constants::JPYC_ADDRESS`). Adding a token whose address differs per chain means changing this signature to take a `ChainId`.
- **`Currency::from_raw_id` matches the raw `&str`, not a parsed `u32`.** This means a non-numeric `master_currency_id` value falls into the same `UnsupportedCurrency` path as an out-of-range numeric one, without a third error variant.
- **`validate_checksum` (EIP-55) is strict, not "uniform case is unambiguous."** `alloy_primitives::Address::parse_checksummed` rejects all-lowercase/all-uppercase input even though it's unambiguous about which address it names — it requires exact mixed-case checksum match. The lenient `parse_address` used by the forward pipeline, by contrast, accepts any casing and even a missing `0x` prefix.
- **Duplicate query params are last-wins in the forward parser** (`to=X&to=Y` → `Y`), intentionally not an error — documented inline in `parse.rs` rather than enforced. The reverse parser errors instead (`DuplicateParam`, compared after percent-decoding the key); see the strict-vs-lenient note above.
- **`ParseError` is `#[non_exhaustive]`.** Adding variants is non-breaking for downstream; inside the workspace, the wasm crate's `errors.d.ts` must still be updated by hand (see wasm boundary below).
- **`ParseError` derives `Serialize` but deliberately not `Deserialize`.** The `MissingParam { name: &'static str }` variant would make `Deserialize` a runtime trap (most deserializers can't hand out `'static` borrowed data), and nothing in the workspace deserializes errors — only serializes them, to throw to JS.
- Amount is `U256` (via `alloy-primitives`), never `u128` — a JPY amount already scaled by 10^18 can exceed u128 range for large-but-legitimate values.

`alloy-primitives` (not `primitive-types`/`ethnum`) was chosen specifically because its `Address` type has EIP-55 checksum generation/validation built in, avoiding a hand-rolled Keccak-256 implementation or an extra `sha3` dependency.

### wasm boundary (`wasm/src/lib.rs`)

JS exports: `parseHashportLink(url)`, `isSupported(url)`, `parseEip681(uri, toName?, linkType?)` (the optional args fill `to_name`/`link_type`, since EIP-681 has no equivalent), `isSupportedEip681(uri)`, `isValidChecksum(address)`; `ParsedLink` has getters plus `toEip681()` and `toHashportLink()` (throws a tagged error).

Three deliberate JS-interop decisions, easy to accidentally regress:
- **Errors throw as plain tagged JS values, not returned Result-likes.** `serde_wasm_bindgen::to_value(&ParseError)` produces `{"kind": "...", ...}` (internally tagged via `#[serde(tag = "kind")]` on the `core` side); documented separately in `wasm/types/errors.d.ts` (shipped in the npm package and re-exported from the main entry by `finalize-package.mjs`, so consumers can `import type { HpwParseError } from "hpw-convert-eip681"`) since wasm-bindgen's generated `.d.ts` can't express "this throws a value of shape X." **`errors.d.ts` must list every `ParseError` variant with its fields** — nothing checks this automatically, and `#[non_exhaustive]` means a new core variant compiles fine while the TS union silently goes stale.
- **`U256` amounts are always decimal strings on the JS side, never numbers or raw BigInt.** `ParsedLink` (the wasm-facing struct) is hand-written with an explicit `From<core::ParsedLink>` conversion rather than derived via `serde-wasm-bindgen`, specifically because `alloy_primitives`'s own `Serialize` impl for `U256`/`Address` emits *hex* (JSON-RPC "quantity" style) — pushing `core::ParsedLink` through `serde-wasm-bindgen` directly would silently produce hex amounts in JS.
- **`chain_id` conversion to `u32` uses `u32::try_from(..).expect(...)`, not `as u32`.** Chain ids can exceed u32 range in general; an `as` cast would silently truncate if a future chain were added. Currently unreachable (all supported chain ids — 1, 137, 8217, 43114 — fit) but deliberately fails loudly rather than truncating.

### Release/publish workflows (`.github/workflows/`)

`ci.yml` (PRs to `main` + pushes to `main`): fmt → clippy → test → wasm-pack nodejs build → smoke test. `release.yml` (triggered on GitHub Release publish): two parallel jobs, `publish-crate` (crates.io) and `publish-npm` (npm), each re-running fmt/clippy/test as a gate before publishing, then verifying the release tag (`vX.Y.Z`) matches the workspace version before publishing.

- **crates.io publishing uses Trusted Publishing (OIDC)** via `rust-lang/crates-io-auth-action@v1` — no long-lived `CARGO_REGISTRY_TOKEN` secret. This has a bootstrap constraint: a brand-new crate cannot use Trusted Publishing for its *first* release (crates.io requires the crate to already exist to register a trusted publisher), so the very first `cargo publish` for any new crate in this repo must be done manually.
- **npm publishing uses a classic `NPM_TOKEN` secret** (no equivalent bootstrap restriction) plus `--provenance`.
- **Both crates.io and npm have immutable published versions** — there is no way to fix a wrong README/metadata on an already-published version; the fix is always a new version bump (`[workspace.package].version` in the root `Cargo.toml`, inherited by both `core` and `wasm` via `version.workspace = true`), not a re-upload.

### Conventions specific to this repo

- **All in-code comments are written in Japanese**, per the author's preference — match this when editing, including doc comments (`///`, `//!`).
- The JPYC contract address (`constants::JPYC_ADDRESS`, shared by all supported chains) is a compile-time-checksum-validated constant (`address!` macro) — if this ever needs to change, re-verify against an authoritative source (not memory), since this project treats "don't guess contract addresses" as a hard rule.
